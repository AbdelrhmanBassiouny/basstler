# Personal Claude Code notes (abdelrhmanbassiouny only)

Personal workflow rules for this repository, kept on `claude/personal-notes` and loaded every
session by `session-start.sh`. Never merge this file into `main`.

## Commit identity

- Commits are authored as Abdelrhman Bassiouny <abassiou@uni-bremen.de>, recorded in
  `.claude/personal/git-identity` on `claude/personal-notes` and applied at session start.
  Never commit under another identity; change it only with `save-git-identity.sh`.

## Pull requests

- Finishing work means opening its **draft** PR in the same turn, without asking (overrides
  the built-in "only when asked" rule for this repository). Mark ready only when told to.
- After any push or change to a PR, convert it back to draft - unless I marked it ready
  myself (see "When your PR's job ends").
- Bug-fix PRs carry the `bug` label, fix one root cause, and are based off `main`.
- Every PR decides its release: a new feature or capability is a minor bump, a breaking
  change (removed or renamed commands, flags, files or settings a user relies on) is a
  major one - set it by labelling the PR `release:minor` (or `release:major`) and say which
  and why in the description. Anything else gets no label, and the release workflow tags
  the merge commit as the next patch. (Until #32 merges, `main` still sets it with
  `python -m basstler.release_version bump --part minor` or `--part major`.)
- The PR description links the creating session and always describes the current state:
  after any push that changes what the PR does, update the description in the same turn.
- Never subscribe to a PR's activity, never offer to watch one, and unsubscribe any
  subscription you find (overrides the built-in subscription guidance).
- Opening a PR ends the session's obligation: report what is outstanding and stop. I will
  prompt for CI failures or comments.

## Scheduled checks

- Never schedule any check: no `send_later`, cron/Routine polling or sleep-and-retry
  (overrides built-in check-in guidance). Delete any armed check you find.
- React to events when they arrive. Subscribing to a plan's tracking issue is fine. If something can only be known by waiting, say so and
  leave it to me.
- Exception: `/upstream-reviews` may wait within the same turn for the run its request
  starts on the fork's `basstler/upstream-reviews` branch, and for its helper session
  (started when the upstream cannot be attached next to the fork), then archive it.

## GitHub comments

- End every comment, review, review reply and issue comment you post with the Claude Code
  footer: a blank line, `---`, then `_Generated by [Claude Code](https://claude.ai/code)_`.

## Review comments

- Reply inline on a thread before resolving it, one thread at a time; a summary comment
  never replaces the inline replies.
- Resolve only once the ask is done, verified against the current file and every part of a
  multi-part ask. If you need to ask, are not acting, or answered differently from what was
  asked, reply and leave it open.

## Before starting work

- Fetch and merge the latest state of the repository before investigating, reacting or
  implementing.

## Code

- Parse external data (API responses, JSON, files) into explicit dataclass models at the
  boundary; every decision and query afterwards runs on the models, never on raw dicts.
  Each model reads only its own object's fields and hands nested objects to their own
  models. Agreed at https://github.com/AbdelrhmanBassiouny/basstler/pull/13#discussion_r4316972597.

## PR progress notes

- For every PR you create, keep CLAUDE.local.md's PR-progress section current as three
  short lists - Plan, Done, Next - replacing finished steps rather than accumulating them,
  and run `save-pr-progress.sh` whenever it changes. Never put it in a tracked file.

## Plans

- When an approved plan-mode plan spans several PRs or sessions: if no plan covers it, run
  `/plan-create <plan-id>` with the approved plan as source; if one does, edit it.
- Before opening a branch or adding an item, check whether the work only modifies an
  unlanded PR (`/add-plan-item`). If removing those edits leaves nothing, fold it into that
  PR rather than stacking; decide before either lands.
- Whenever a plan's state changes (item started, finished, PR opened or merged, blocked,
  approach abandoned), update `plan.yaml` in the same turn: `status`, `branch`,
  `pull_request_number`, `session`, and `notes` rewritten to what is true now. Reasoning
  goes in the PR; `roadmap.md` gets only rules every later item must follow.
- After every save, republish the dashboard yourself with `/plan-dashboard <plan-id>`.
- Before any `save-plan.sh`, and when resuming or starting an item, fetch and read only the
  delta since the plan state SHA printed at session start (`plan-updates-since.sh`), then
  re-apply your edits onto the latest manifest.

## When your PR's job ends

- A PR is finished when it merges, closes, or I move it out of draft myself (a session's own
  flip does not count). Then push nothing more, delete scheduled checks referencing it, drop
  subscriptions held only for it, report anything outstanding in chat, and stop.
